# DysonProtocol L2 "Rounds & Slots" – **TewProtocol Specification v0.3**

> **Status:** Draft (supersedes v0.2)
>
> This version removes the packet-queue abstraction and introduces **separate storage** for L1 and L2 state/logic. L1 state and logic are stored independently from L2 round commits. Each layer can upgrade only its own `core_logic`. Decorators were removed in favour of naming-based visibility.
>
> **v0.3.1 Update:** Added built-in bank escrow functionality to enable payment channels and other financial applications. The TEW Protocol now automatically handles incoming bank transfers and provides L1 logic with functions to manage escrowed funds.

---

## 0 · Scope & Purpose

This document specifies the **TewProtocol**, a framework for building deterministic Layer-2 (L2) Proof-of-Authority (PoA) applications ("TewApps") that execute atop the **Dyson Protocol** blockchain (Layer 1).  Version 0.3 reflects a conceptual redesign that eliminates the *TewPacketQueue* and models cross-layer coordination through separate L1 and L2 state management.

---

## 1 · Architecture Overview

| Component | Layer | Responsibility |
|-----------|-------|----------------|
| **Dyson Protocol** | **L1** | Cosmos-SDK blockchain with a Python execution engine. Provides storage, consensus, and transaction routing. |
| **TewProtocol Script** | **L1** | A Python smart contract deployed once. Manages creation of L2 instances, on-chain storage, and round progression. |
| **TewApp Instance** | **L1 / L2** | A self-contained application with separate storage for:<br/>• **L1 state & logic** (stored at `tew/{id}/l1/state` and `tew/{id}/l1/core_logic`)<br/>• **L2 round commits** (stored at `tew/{id}/l2/rounds/{round}`) containing L2 state & logic |

Key principles:
1. **Separate Storage Model** – L1 state/logic and L2 round commits are stored independently on-chain.
2. **Strict Layer Boundaries** – L1 logic can only interact with the blockchain through TEW-provided functions. L2 logic can only communicate with L1 logic, not directly with the blockchain.
3. **Round-Based Determinism** – All off-chain computation occurs in discrete rounds. Only the checkpointed head is authoritative on-chain.
4. **Asynchronous Progress** – The cadence of L2 round progression is *not* tied to L1 block production; an L2 may advance faster (multiple rounds per L1 block) or slower (pause for hours) provided it respects timeout and monotonicity rules.

## 2 · Data Model

### 2.1 Storage Layout

**L1 Storage:**
* `tew/{tew_id}/l1/state` – JSON-serialized L1 state dictionary
* `tew/{tew_id}/l1/core_logic` – Python source code for L1 logic
* `tew/{tew_id}/l1/meta` – Metadata including timeout, core_logic_hash, started_at

**L2 Storage:**
* `tew/{tew_id}/l2/rounds/{round:010d}` – L2 round commit for specific round
* `tew/{tew_id}/l2/latest_round` – Current round number

**Bank Escrow Storage:**
* `tew/{tew_id}/balances/{denom}` – Escrowed coin balance for each denomination

**Slot Storage:**
* `tew/{tew_id}/slots/{round}/{member}/{slot_hash}` – Slot submission record where `slot_hash` is the SHA256 hash of the canonical JSON representation of `slot_data`. Structure:
  ```json
  {
    "valid": true/false,
    "slot_data": { /* full slot payload */ },
    "submitted_by": "dys1...",
    "submitted_at": 1725123456,
    "validation_error": "optional error message if valid=false"
  }
  ```

### 2.2 L2 Round Commit Structure

A canonical JSON object stored for each L2 round:
```jsonc
{
  "meta": {
    "round": 42,
    "core_logic_hash": "0x…",
    "committee": ["dys1...", "dys1..."],
    "timeout": 30,
    "started_at": 1_725_123_456
  },
  "state": { /* L2 application state */ },
  "core_logic": "# L2 Core Logic Python source..."
}
```

### 2.3 Slot Payload (`slot_data`)

Each committee member submits exactly one slot per round:
```jsonc
{
  "round": 42,
  "participant": "dys1...",
  "slot_logic": "# Python code to execute in round",
  "embedded_l1_state": { /* L1-provided data */ },
  "l1_block_header_info": {
    "block_height": 123456,
    "block_hash": "0x...",
    "timestamp": 1725123456
  }
}
```

The `embedded_l1_state` field contains data deterministically generated by the L1 logic. Committee members include the current block header info when creating slots. The L1 core logic MUST provide a function `generate_embedded_slot_state(slot)` that the TEW protocol calls to generate this field. The function receives the slot data (including `l1_block_header_info`). Historical state queries are not supported; designs should encode necessary data in-state or indices.

## 3 · Execution Flow

The protocol exposes **six** primary entry-points on the TewProtocol script. All are callable by any user except where noted.

### 3.1 `l1_genesis(initial_genesis)` – create a TewApp
Allocates a new `tew_id`, stores:
- L1 state at `tew/{id}/l1/state`
- L1 core logic at `tew/{id}/l1/core_logic`
- L1 metadata at `tew/{id}/l1/meta`
- L2 round 0 commit at `tew/{id}/l2/rounds/0000000000`
- Initializes empty escrow balances at `tew/{id}/balances/{denom}` (populated when funds are received)

### 3.2 `l1_submit_slot(tew_id, signed_slot_tx)` – submit a single slot
Process:
1. Verifies ADR-036 signature to identify the submitter
2. Extracts slot data and calculates `slot_hash = sha256(canonical_json(slot_data))`
3. Validates `embedded_l1_state` by calling `generate_embedded_slot_state(slot, slot.l1_block_header_info.block_height)`
4. Stores submission at `tew/{tew_id}/slots/{round}/{member}/{slot_hash}` with:
   - `valid: true` if validation passes
   - `valid: false` if validation fails (with error message)
   - `submitted_by`: address from signature verification
   - `submitted_at`: current timestamp
5. Multiple submissions allowed per member/round, but only the first valid slot is used for round progression

This design enables fraud detection and accountability by tracking all submission attempts.

### 3.3 `l1_call_tew_app(tew_id, func_name, *args)` – invoke public L1 logic
Executes the named **public** function inside `l1_core_logic` (one that does **not** start with `_`). The function:
- May read the latest L2 state (read-only access)
- May mutate L1 state
- May NOT directly send blockchain transactions (`_msg` is not available)
- Must use only TEW-provided helper functions for blockchain interaction

**Bank Escrow Processing:**
When any user executes a public L1 function via `l1_call_tew_app`, they can attach bank transfer messages to their transaction. The TEW Protocol automatically processes these attached messages before executing the L1 function:

1. The calling user attaches one or more `cosmos.bank.v1beta1.MsgSend` messages to their transaction
2. The TEW Protocol iterates through all attached messages via `get_attached_messages()`
3. For each `cosmos.bank.v1beta1.MsgSend` where `to_address == get_script_address()`:
   - Increments `tew/{tew_id}/balances/{denom}` by the transferred amount atomically
   - Makes the deposited amounts immediately available to the L1 function via `get_escrowed_balance(denom)`
4. The L1 function then executes with access to:
   - The attached messages (to identify senders and amounts)
   - The updated escrow balances
   - **Critical**: The L1 function is responsible for attributing these funds to the correct users according to its own logic

**Example**: A user wanting to deposit 1000 DYS into a payment channel would:
- Attach a `MsgSend` transferring 1000 DYS to the TEW script address
- Call `l1_call_tew_app(tew_id, "process_deposit")`
- The L1 `process_deposit` function would read the attached message, identify the sender, and credit their internal balance

**Command Line Example**:
```bash
# CORRECT: Attach bank send to L1 function call
dysond tx script exec \
  --script-address <tew-protocol-address> \
  --function-name l1_call_tew_app \
  --args '["tew_000001", "process_deposit"]' \
  --attached-message '{"@type":"/cosmos.bank.v1beta1.MsgSend","from_address":"<user>","to_address":"<tew-protocol-address>","amount":[{"denom":"udys","amount":"1000"}]}' \
  --from <user>

# WRONG: Direct transfer (funds will be lost!)
dysond tx bank send <user> <tew-protocol-address> 1000dys
```

### 3.4 `l1_checkpoint_round(tew_id, round_height, signed_slots[])` – fast-forward checkpoint (NORMAL FLOW)
Stores a pre-computed L2 round commit at `round_height`. All committee members must have previously submitted valid slots via `l1_submit_slot`. The `signed_slots[]` array contains the slot transactions for verification. No on-chain execution of `_apply_slots` occurs. This is the preferred method for round progression when off-chain consensus works. Does not modify L1 state.

### 3.5 `l1_signal_force_onchain(tew_id, round_height)` – signal intent to force on-chain execution
Announces that off-chain consensus has failed and starts a timeout period for collecting slots:
1. Can only be called for the next round (`current_round + 1`)
2. Records a force signal with timestamp and timeout duration
3. Committee members have the timeout duration to submit their slots
4. Once signaled, `l1_progress_round` can execute when either all slots are present OR the force timeout expires

### 3.6 `l1_progress_round(tew_id)` – on-chain round execution (FALLBACK FLOW)
Executes L2 logic on-chain when off-chain consensus has failed. Requires either:
- A prior `l1_signal_force_onchain` call (preferred), OR
- The normal round timeout has elapsed (backward compatibility)

Process:
1. Checks for force signal or normal timeout expiry
2. Collects valid slots from storage (queries `tew/{tew_id}/slots/{round}/{member}/*` for entries with `valid: true`)
3. If force signal exists: proceeds when all members have valid slots OR force timeout elapsed
4. If no force signal: proceeds when all members have valid slots OR normal round timeout elapsed
5. Executes `_apply_slots` from L2 core logic with collected valid slots to produce new L2 state
6. Persists the new L2 round commit
7. Cleans up processed slot storage entries to save space
8. **No automatic L1 state mutations** – any L1 changes require separate `l1_call_tew_app` transactions

### 3.7 `l1_force_round_onchain(tew_id, round_height, signed_slot_txs[])` – legacy timeout recovery
Legacy mechanism for forcing round progression after normal timeout has elapsed. Accepts whatever slots are available and executes the round transition on-chain. Being superseded by the signal/progress flow.

### 3.8 Additional Implementation Functions
The TEW Protocol implementation may include additional helper functions not part of the core protocol:
- `list_tew_instances()` – List all TEW instance IDs
- `get_tew_info(tew_id)` – Get current state information for a TEW instance
- `reset_tew_data()` – Clear all TEW data (testing only)

The implementation may also expose a read-only WSGI interface for monitoring TEW instances via web dashboard.

## 4 · Public API (Function Visibility Rules)

### Core Logic Requirements

**L1 Core Logic Requirements:**
`l1_core_logic` MUST define **`generate_embedded_slot_state(slot)`** (public) which deterministically generates the `embedded_l1_state` data for a slot. Historical queries via height are not available.

**L2 Core Logic Requirements:**
`l2_core_logic` MUST define **`_apply_slots(l2_state, slots)`** (private) which computes the next L2 state.

### Visibility Conventions
* **Public L2 functions** – Any top-level function in `l2_core_logic` not starting with `_` is callable from `slot_logic`
* **Public L1 functions** – Any top-level function in `l1_core_logic` not starting with `_` is callable via `l1_call_tew_app`
* **Private helpers** – Names prefixed with `_` are internal and not exposed

### Available Functions in Execution Contexts

**L1 Core Logic has access to:**
- `l1_state` (mutable) – The L1 state dictionary
- `l2_state` (read-only) – Latest L2 state from most recent round
- `_query(params)` – Query blockchain state at current height only
- `get_block_info()` – Current block header info only (no historical block headers available)
- `get_script_address()` – TEW instance address
- `get_executor_address()` – Current caller address
- `get_attached_messages()` – Access transaction's attached messages (essential for identifying who sent escrowed funds)
- `get_escrowed_balance(denom)` – Query escrowed balance for a denomination
- `send_coins(transfers)` – Send escrowed coins to recipients (see below)
- **NOT** `_msg` – L1 cannot directly send transactions

**L2 Core Logic has access to:**
- `json` module
- `tew_eval` – For executing slot code safely

**Bank Escrow Functions:**

The TEW Protocol provides built-in bank escrow functionality. **Important**: Escrow only occurs when users attach `MsgSend` messages while calling L1 functions. The L1 function must handle fund attribution:

1. **`get_escrowed_balance(denom)`** – Returns the current escrowed balance for a specific denomination
   - Queries `tew/{tew_id}/balances/{denom}`
   - Returns 0 if no balance exists

2. **`send_coins(transfers)`** – Sends escrowed coins to recipients
   - `transfers`: List of dictionaries with format: `[{"amount": "1000", "denom": "udys", "to_address": "dys1..."}, ...]`
   - Validates sufficient balance exists for each denomination
   - Decrements `tew/{tew_id}/balances/{denom}` for each transfer in a single atomic transaction
   - Executes `cosmos.bank.v1beta1.MsgSend` for each transfer
   - Raises error if insufficient balance

Example usage in L1 core logic:
```python
def process_deposit():
    """Process deposits from attached messages.
    CRITICAL: This function must properly attribute funds to users!
    """
    messages = get_attached_messages()
    for msg in messages:
        if msg.get("@type") == "/cosmos.bank.v1beta1.MsgSend":
            # Identify who sent the funds
            sender = msg["from_address"]
            
            # Process each coin in the transfer
            for coin in msg["amount"]:
                amount = int(coin["amount"])
                denom = coin["denom"]
                
                # ATTRIBUTION: Credit the sender's internal balance
                balances = l1_state.setdefault("balances", {})
                user_balance = balances.setdefault(sender, {})
                user_balance[denom] = user_balance.get(denom, 0) + amount
    
    # The escrowed balance is now available via get_escrowed_balance()
    return {"processed": True}

def process_withdrawal(address, amount, denom):
    # Verify user has internal balance before withdrawing
    user_balance = l1_state.get("balances", {}).get(address, {}).get(denom, 0)
    if user_balance < amount:
        raise ValueError("Insufficient user balance")
    
    # Check escrowed balance
    escrow_balance = get_escrowed_balance(denom)
    if escrow_balance < amount:
        raise ValueError("Insufficient escrowed balance")
    
    # Send coins (automatically decrements escrow)
    send_coins([{
        "amount": str(amount),
        "denom": denom,
        "to_address": address
    }])
    
    # Update internal accounting
    l1_state["balances"][address][denom] -= amount
```

**Planned Helper Functions** (not yet implemented):
- `upgrade_l1_logic(new_code)` – Allow L1 logic to self-upgrade

**Committee Management:**
The committee membership list is managed by L2 core logic as the source of truth. The L2 core logic should import and call TEW-provided functions like `tew.add_member(address)` and `tew.remove_member(address)` to modify the committee stored in round commits.

## 5 · Security & Invariants

1. **Layer Isolation** – L1 can only use TEW-provided functions, L2 can only communicate with L1
2. **Storage Separation** – L1 state/logic stored separately from L2 round commits
3. **Slot Submission Tracking** – All slot submissions are stored with their hash and validity status. Invalid slots (e.g., wrong `embedded_l1_state`) are tracked as `{valid: false}` for accountability. Multiple submissions for the same `(round, member)` are allowed but only the first valid one is used for round progression. This enables detection of equivocation attempts while allowing members to correct invalid submissions
4. **Committee Participation** – All members must submit slots every round, or liveness halts until timeout
5. **Determinism** – Core logic may not perform I/O or non-deterministic operations
6. **Embedded State Determinism** – `embedded_l1_state` is generated deterministically based on historical state at the provided block height. Since historical block headers are not queryable, committee members must include current block info when creating slots
7. **Upgradability** – L2 rounds may update `l2_core_logic`; L1 functions may update `l1_core_logic` (helper pending)
8. **Bank Escrow Security** – 
   - Only attached messages when executing public TewApp L1 core_logic functions are automatically escrowed
   - **Important**: Direct transfers to the TEW script address (not attached to L1 function calls) are NOT escrowed and will be lost
   - L1 functions are fully responsible for proper fund attribution based on attached message contents
   - Escrowed balances can only be decreased via `send_coins()` function calls from L1 logic
   - The TEW Protocol tracks escrowed balances separately from L1/L2 state to prevent manipulation
   - Total escrowed coins always equals sum of all `tew/{tew_id}/balances/{denom}` entries

## 6 · Upgrade Path & Compatibility

| Change from v0.2 | Impact | Migration Path |
|------------------|--------|----------------|
| Removal of Packet Queue | All queue-related fields deleted | Direct function calls between layers |
| Separate L1/L2 storage | Clear storage boundaries | L1 state no longer in round commits |
| `embedded_l1_state` | Optional L1-determined data in slots | L1 decides what data slots should include |
| Force signal mechanism | Explicit timeout for on-chain execution | Use `l1_signal_force_onchain` before `l1_progress_round` |
| Bank Escrow | Built-in coin deposit/withdrawal support | L1 logic manages deposits via `send_coins()` |

## 7 · Open Questions & Future Considerations

### Committee Member Management
- **Member Key Rotation** - Currently uses Dyson addresses; no mechanism for rotating keys
- **Unresponsive Members** - Only timeout mechanism available; intentional design choice but open to better ideas
- **Member Discovery** - How new members discover current committee membership (out of scope)
- **Staking** - How to handle staking, slashing, and rewards for committee members


### Round Hash Storage  
- **Multiple Valid Checkpoints** - If two valid checkpoints are submitted for same height, both are stored at `tew/{id}/rounds/{round}/{round_hash}` to detect misbehavior. The L2 core logic must implement fork choice rules.

### Storage & Scalability
- **Slot Storage Growth** - Slot submissions accumulate without automatic cleanup (except after round progression)
- **Round Archival** - No defined strategy for archiving old round data
- **State Pruning** - No mechanism for pruning historical state

### Out of Scope
- **Off-chain Communication** - How committee members share L2 state for normal flow consensus
- **State Synchronization** - How new committee members catch up to current state  
- **Chain Reorganizations** - Handling L1 blockchain reorganizations
- **Cross-TEW Communication** - Inter-TEW messaging or shared state

### Recovery Scenarios
- **Lost Off-chain Data** - System can theoretically continue from last on-chain L2 round commit
- **Consensus Rules** - Off-chain consensus follows simple rule: `tew.l2._apply_slots(round, slots) → next_round`, where TEW uses the round's L2 core logic to process the slots deterministically
